# 两个个人网站的Linux服务器容量估算

评估日期：2026-11-12。面向Luckypig Space与ZYT Space，共用一台Linux x86服务器、各自独立网站实例和数据。以下是初期低访问量、少量面试访客的容量建议，未对真实服务器做负载测试，不是性能保证或报价。

## 建议规格

| 场景 | CPU / 内存 | SSD | 公网出站带宽 | 说明 |
| --- | --- | --- | --- | --- |
| 低流量试部署 | 2核 / 4GB | 60–80GB | 5–10Mbps | 可以作为低负载起点；两套完整后台同时启动、更新和构建时余量较小 |
| 两站日常使用，推荐 | 4核 / 8GB | 100GB | 10Mbps起 | 适合初期展示、面试浏览和外部模型API会话，后续观察再扩容 |
| 多人同时观看录屏 | 4核 / 8GB | 100GB起，随媒体增加 | 20Mbps起或视频走对象存储/CDN | 视频更影响出站带宽和流量，而不是普通网页CPU |

这是一台服务器承载两个站的总规格，不是每个站各买一台。调用公网DeepSeek等模型API时，不需要本机GPU，也不需要为推理配置显存。若以后在本机运行模型，需重新评估，以上建议不适用。

## 估算依据

两站各自使用完整Halo后台时，运行2个Node网站、2个Halo、2个PostgreSQL，共6个业务容器；宿主可共用Nginx反向代理。共用网站镜像，分别配置Compose项目名、域名/端口、数据库和附件/模型设置卷。数据库不必对公网开放。

[Halo官方准备说明](https://docs.halo.run/guide/prepare)建议至少1GB RAM获得更好的体验，并建议SSD。这个建议针对Halo本身，不能当作“两站加数据库总共1GB”。当前Compose给每个Halo的Java堆设置为256–512MB；实际进程还包含非堆、线程等内存，不能只把Xmx相加估算整机需求。4GB可试用，8GB给两个后台、数据库、系统和部署操作留出余量。

ZYT当前文件资料模式仅需Node读取公开JSON，不依赖Halo；若只运行这一预览，实际负载会更低。完整Compose模板仍会预留并启动它的Halo和数据库。推荐规格按未来两套完整站点考虑。

## 带宽与流量

云服务器标注的“10M/20M”通常指Mbps公网出站带宽，不是每秒10MB/20MB。以[阿里云官方网络带宽说明](https://www.alibabacloud.com/help/en/ecs/user-guide/network-bandwidth)为例，购买的公网带宽是出站带宽，5Mbps约0.625MB/s；因此10Mbps理论约1.25MB/s、20Mbps约2.5MB/s，实际还受协议和线路影响。套餐显示的峰值或“最高可达”不等于持续保障；同时核对出站流量配额和超额费用。

粗略规划方法：同时观看人数 × 单路视频平均码率 × 1.3预留系数。例如未来录屏按3Mbps编码，3人同时看约需11.7Mbps，因此20Mbps比10Mbps更从容；预加载和拖动定位还会造成突发请求。此例是假设，不代表当前视频实测码率。

目前已处理的三条展示录屏体积约4.3、7.6、13.2MB，时长约62.5、52.5、174.4秒，平均码率约0.55、1.16、0.61Mbps（由既有处理记录换算）。它们比较轻，不能据此推断未来所有视频也一样。初期零散访客10Mbps可作为起点；有多个高码率录屏同时播放时，优先增加带宽或把媒体放到对象存储/CDN。

流量与带宽是两件事：100MB的视频完整播放1000次，约产生100GB出站传输，还未计重复下载、页面和其他请求。共享同一服务器时，两站一起占用同一个出站上限与流量包。

## 磁盘和后续观察

100GB SSD用于系统、镜像、两个站点数据、媒体、日志和少量本地备份。视频容量与备份保留份数会决定增长速度；给磁盘留出约20%以上余量，备份另保留一份服务器之外的副本。本次不复制现有录屏、数据库或Key到新站。

上线后再观察：两套后台同时启动/重启后的内存余量，CPU持续利用率、磁盘余量、实际出站峰值、2–3位访客同时播放/定位的体验，以及模型请求延迟和错误率。网页文字打开快但视频缓冲慢时，先检查媒体码率和带宽；这时单纯加CPU通常无助于视频传输。

本次未购买服务器、未调整运行参数、未执行远程部署或真实并发压测。
